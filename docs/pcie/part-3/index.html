The Link is up. Why is the endpoint still invisible?

Trace Configuration Requests, bus numbers and discovery through the PCIe hierarchy.

A healthy link is not enough

Assume the link is stable and the Data Link Layer is active, but the operating system still cannot discover the endpoint. The next investigation is the configuration transaction path.

Discovery depends on reaching the Function and receiving a valid Completion. BAR allocation is a later boundary.

Follow bus routing

Software identifies a Function using Bus, Device and Function within a PCI segment. Bridge bus number registers define which bus numbers exist below each bridge. Incorrect secondary or subordinate bus programming can prevent a Configuration Request from reaching the endpoint.

Root Port → Switch bridge Functions → Endpoint

Type 0 and Type 1 requests

Configuration routing uses Type 1 requests to travel through the hierarchy toward the target bus, with Type 0 access on the target bus. These request types should not be confused with the Type 0 and Type 1 configuration header layouts.

Debug one boundary at a time

  1. Confirm stable link and Data Link status.
  2. Record the intended topology and bus numbering.
  3. Trace the Configuration Request through the bridge hierarchy.
  4. Check whether a Completion returns and whether it reports success.
  5. Correlate the hardware trace with the operating system’s discovery attempt.

At Gen6 and Gen7 rates, decode the physical transport before interpreting the configuration transaction. A retimer is a physical observation point, not another enumerated bridge Function.

The next boundary

Once identity reads succeed, the endpoint is configuration visible. Making its registers usable requires resources and an address path. That is the subject of Part 4.
