PCIe Systems / PART 4

The endpoint is visible. Why can the driver still not use it?

Understand BAR sizing, address allocation, bridge windows and a usable MMIO mapping.

Visible does not mean usable

The endpoint appears as 03:00.0. Configuration reads return its Vendor ID, Device ID and capabilities. The driver matches the Function, but BAR0 has no assigned address.

Configuration visibility proves that the configuration route works. MMIO usability also requires a valid address allocation, bridge windows covering that address and Memory Space Enable at the endpoint.

BARs and bridge windows have different jobs

A Base Address Register describes an endpoint resource aperture. A 32 bit memory BAR uses one register position; a 64 bit BAR uses an adjacent pair. A bridge memory window determines which address ranges the bridge forwards downstream.

Allocating the endpoint BAR is insufficient if a parent bridge cannot forward its complete range.

Sizing and address placement

Enumeration software probes the implemented BAR size under controlled conditions and allocates an appropriately sized and aligned range. A 32 bit memory BAR must lie below 4 GB. A 64 bit memory BAR can lie below or above 4 GB.

Available host bridge apertures and reserved regions still constrain allocation. A 64 bit CPU does not by itself guarantee sufficient MMIO space. Above 4G decoding is a platform firmware option related to that resource map; it does not change the endpoint’s DMA address width.

Do not manually size a live BAR. Use the operating system’s resource information and controlled enumeration procedures.

A worked allocation failure

Consider a 256 MB, 64 bit prefetchable resource using the BAR0/BAR1 pair. The downstream bridge window provides only 128 MB and cannot grow in the current map. The endpoint remains configuration visible, but there is no valid allocation path for that resource.

This is an illustrative address map, not a claim about the aperture size of a particular accelerator. The repair is to provide a suitable region and valid windows throughout the hierarchy, then enable memory decoding.

Follow the driver in order

Resource assigned → Region reserved → BAR mapped → Register access

On Linux, device enable, region reservation and BAR mapping are separate steps. Check every return value. Use the PCI core’s resource records: CPU physical addresses and PCI bus addresses are not necessarily identical on every platform.

A practical debug sequence

  1. Save the topology, boot log, configuration space and resource map.
  2. Confirm stable configuration reads for the endpoint.
  3. Inspect BAR type, size, alignment and assigned range.
  4. Check the host bridge’s available MMIO apertures.
  5. Walk every parent bridge window and verify full containment.
  6. Check endpoint Memory Space Enable.
  7. Identify the exact driver step that fails.

Gen6 and Gen7 increase transport capability, but these resource and driver boundaries still require separate validation.
